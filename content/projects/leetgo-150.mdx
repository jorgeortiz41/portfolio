## Context

I wanted to learn Go, and reading documentation teaches you syntax rather than
what a language is like to work in. Algorithm problems are a reasonable forcing
function: each one stresses a different data structure, and you find out quickly
where the standard library is generous and where the type system gets in the
way.

## Approach

One self-imposed rule, written at the top of the repo: **no Copilot and no
ChatGPT.** The point was to learn Go, and autocompleting my way through it would
have produced a repo full of solutions I could not explain.

I did not keep the rule perfectly, so the README marks every problem where I
took help with an asterisk — currently 8 of them — along with notes on what I
still did not understand afterwards. Keeping that visible is the part I would
defend: a practice log that hides where you struggled is not much of a log.

Some problems got more attention than the answer strictly required. For
[H-Index](https://github.com/jorgeortiz41/leetGo-150/blob/main/hIndex.go) I
wrote two solutions and benchmarked them against each other, using goroutines to
run the timing, and measured one at roughly **24× faster** on larger inputs.
That is the habit I actually wanted out of this: not "does it pass", but "which
one is faster, and by how much, and can I show it".

## Status

**Paused, and honest about it.** 22 of the 150 solved, spanning arrays and
strings, two pointers and sliding window — three of the topic areas, not all of
them. Two more are half-finished and marked in-progress in the README, including
one that passes locally but fails a LeetCode case I have not diagnosed.

Nothing has landed since June 2026. I plan to pick it back up later this year
and work the remaining problems across several languages rather than only Go,
which makes the comparison itself part of the exercise.

I am leaving this here mid-run rather than quietly dropping it. The progress is
in the README either way, and a portfolio that only shows finished things is not
an honest picture of how anyone learns.
